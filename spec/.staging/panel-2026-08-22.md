## Divergences

### D1 — SR-010 (name↔dir): which command surfaces it, and does it fire without format context? [ACTIONABLE → amend]
- **Reading A (reader A):** lives in the graph pass; on a lone-file lint with no context, default to "directory governs".
- **Reading B (reader B):** lives in graph pass; on a lone file, walk up the tree to detect format, else default.
- **Reading C (reader C):** lives in graph pass; **does NOT fire on a content-only single-file lint** with no discoverable format.
- **The fork that matters:** all three place the rule in the **graph** pass, but SCN-003 says "when the author **lints** it," and the acceptance test (`correctness-real` task 13) runs `cmd: lint`. If the rule lives only in `graph`, `lint` never emits `name-dir-mismatch` and task 13 can never go green — a spec/test/implementation three-way mismatch.
- **Proposed disambiguation:** amend SCN-003 to say the check surfaces on **both** `lint` and `graph` (the rule needs only the SKILL.md's own directory, which a lone-file lint has), and add an acceptance criterion: when the format is genuinely undetectable, the finding still fires with the default "directory name governs" wording (Reading A over C). Alternatively, retarget task 13 to `graph`. Recommendation: the former — authors run `lint`, so `lint` must surface it.

### D2 — SR-012 (portable-finding severity): error vs warning [ACTIONABLE → amend]
- **Reading A:** `error` — a non-portable field will hard-fail on claude.ai/Skills-API upload; INV-1 only scopes default mode, so an opt-in-mode error is legal.
- **Readings B & C:** `warning` — the field is valid *in Claude Code*; overloading `error` (which everywhere else means "won't work in Claude Code") blurs a meaning INV-1 relies on.
- **Acceptance test + majority:** task 18 expects `{non-portable-field, warning}`; 2 of 3 readers pick warning.
- **Proposed disambiguation:** pin severity = **warning** in SR-012 (and add to SR-105's warning list). Reader A's argument is defensible but the meaning-preservation + acceptance-test alignment wins. Amend to remove the ambiguity.

### D3 — SR-013 (plugin detection): marketplace-gated vs independent branch [ACTIONABLE-lite → accept, note for impl]
- **Reading A:** keep the root-`SKILL.md` check under the existing `hasMarketplace` gate.
- **Readings B & C:** SCN-006's fixture has only `.claude-plugin/plugin.json` and **no** `marketplace.json`; `detectFormat` currently requires `marketplace.json` before any skill check, so a new **independent** detection branch (root `SKILL.md` + `plugin.json`, no marketplace requirement) is needed or the fixture is misclassified.
- **Resolution:** the spec fixture settles it — accept **independent branch** (B/C). This is a case of reading A under-reading the existing gate, not a true spec ambiguity, so no amendment needed; recorded here so the implementer does not gate SR-013 behind `marketplace.json`.

### D4 — SR-006 (bare-path grammar): how to constrain bare-path matching [accept → decision-ledger]
- All three: links + bare relative paths, fenced blocks stripped. They differ on the bare-path grammar:
  - **B:** extension-anchored — a token with a slash and a file extension, no surrounding prose punctuation.
  - **C:** prefix-anchored — only known bundle prefixes (`scripts/`, `references/`, `assets/`) or a recognized non-`.md` extension.
  - **A:** unspecified beyond "bare relative-path pattern".
- **Why it matters:** this is the INV-1 false-positive dial — too loose trips on prose. Not a behavioral fork the acceptance tests currently distinguish (fixtures use `scripts/render.sh`, which both grammars match).
- **Resolution:** accepted ambiguity → generator's decision ledger. Recommended conservative default: match a bare path only if it (a) is outside a fenced block AND (b) either starts with a known bundle prefix OR ends in a file extension — i.e. C's prefix rule OR B's extension rule, whichever fires. Revisit if the adversarial holdout set grows a prose-path false positive.

### D5 — SR-016 (tokenizer): regex vs linear depth-scanner [accept → recommend scanner, INV-4]
- **Readings A & C:** linear paren-depth-tracking scanner — linear-time by construction, satisfies INV-4, handles comma-only separation (`Bash(...),Read`).
- **Reading B:** a single regex (`\w+\([^)]*\)|[^\s,]+`), self-described as "sufficient to pass the stated acceptance test," but reader C flags it may misfire on comma-only input and sits closer to the ReDoS class INV-4 prohibits.
- **Resolution:** accepted ambiguity → recommend the **linear scanner** (A/C majority + INV-4 makes it near-decided). No spec amendment; implementation decision recorded.
